# NetRoute v6.2 Three-Connection Smart Routing Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Run Smart routing in Phone, LAN and Wi-Fi profiles with explicit per-rule targets and safe non-metered fallback, preserving the existing user controls and two-bucket usage history.

**Architecture:** Use ConnectionId for physical routing/profile identity and a small RuleTarget enum for Home versus literal LAN/Wi-Fi/Phone targets. Keep one pure selection policy, one sing-box compiler and the existing gated lifecycle controller; generalize the existing outage bookkeeping by target rather than introducing another routing engine. Existing RouteExit remains only at the two-way catalog/usage boundary; Wi-Fi bytes continue to use the LAN usage bucket until v6.3.

**Tech Stack:** .NET10/net10.0-windows, WPF/WinForms, pinned sing-box1.14.2, xUnit and existing handwritten networking/host/API/time fakes.

**Spec:** docs/superpowers/specs/2026-10-22-netroute-v6-wifi-connection-design.md — Smart routing, phase v6.2, identity tests; existing off/Not used semantics remain.

## Review Focus

1. Physically connected LAN is off/Not used: no remembered real LAN bind or selector reference can send traffic over it; compile a valid waiting configuration (Tasks2-4).
2. No Phone, Wi-Fi only, or no answering home connection: Smart can run on usable non-metered main; Home uses Wi-Fi or waits, never silently Phone (Tasks2-4).
3. Profile/adapter/target changes during an outage or stale popup click: no cross-target/mobile permission leaks; selectors retry failed API calls and notify only after applied recovery (Task4).
4. Same app/site in multiple profile lists with changed explicit Exit: routing precedence is deterministic, fingerprints change, IDs stay stable and usage stays one row (Tasks1,3,5).
5. Sing-box's TUN is Windows' active route: default-exit resolution must preserve the physical carrier, not feed its own TUN result back into fallback (Tasks2,4).

**Controller rules:** dictionaries keyed RuleTarget hold explicit-use-main, healthy count, outage start, popup/keep-waiting and pending-back-toast; preserve existing gate, crash budget, API grace, failure/retry and cleanup behavior. Derive answering from used/present gateway+IPv4 and per-ID latency. Normal traffic waits only if no permitted normal candidate answers. Override recovery means the literal target itself answers (LAN/Wi-Fi/Phone), or any eligible home connection answers for Home: do not announce "LAN back" merely because Wi-Fi answered. Three consecutive healthy Apply checks end an override; one miss resets count. UseMain verifies the same target/main still waits, main equals current WantedExit and is eligible; stale click no-op. Changing profile/off flags/adapter choice invalidates inapplicable overrides, so mobile permission cannot migrate to another target/profile. KeepWaiting is target-specific.

**Bindings/config key:** chosen IsUsed slots only, with per-ID last-known names for genuinely disconnected chosen slots; seeded existing LastLanInterface only for an eligible LAN slot. Clear stale binding on changed override identity; off/Not used can retain cache but never emits/binds it. Key includes all chosen IDs/names, LAN DNS, rule fingerprint, candidate membership and override membership. Health-selected exits use API updates; membership changes (notably adding/removing Phone for an override) restart config safely. No second host starts if prior Stop failed. Start can run on usable LAN/Wi-Fi with no Phone; missing Phone rules wait/use allowed currentPath. Auto/admin/disabled/faulted guards remain; remove WifiPaused/NeedsBoth assumptions. If WantedExit null, stop/pause with truthful no-connection message.

**Applied state:** track selected exit per target. A failed SelectAsync never advances applied state or emits back toast; retry next Apply. Only notify recovery after correct selector/config actually applied, with target label. Waiting names come from target's recent matching failures; retain existing sustained outage delay and single-popup suppression per outage. Explicit off cannot continue through an old live config: restart/stop the old binding through existing lifecycle before publishing changed applied routing.

**Action identity/eligibility:** controller owns a monotonically increasing generation counter that never resets within its lifetime, assigned per target on intent/profile/main/binding/off context changes and a new target waiting-outage transition, not on stable probe/grant refreshes. Validate request.Generation and request.Target/Main against current server-owned state under the gate; A->B->A cannot revive the old snapshot. Both popup and Config capture the immutable snapshot when the action is rendered/created, never reacquire a fresh generation on click. Qualified but unanswered current main may receive an explicit pending grant (approved-plan eligibility); policy still selects unavailable and UsingMain remains false until the selector actually applies that main. Such a Wi-Fi grant never permits Phone after automatic carrier change. KeepWaiting also validates the same generation and cannot suppress a later outage. Another target's stable action is not invalidated merely by an unrelated target outage.

**TUN resolver:** create `SmartRoutingPathResolver.Resolve(bool smartActive,ConnectionId appliedExit,int? queriedIndex,int? tunIndex): InternetPath?` in Core; returns PathOf(appliedExit) only for active Smart and queried TUN index, otherwise null. App's ExternalPathResolver delegates to it, eliminating the old LAN/Phone ternary. Tests send every ID through it.
