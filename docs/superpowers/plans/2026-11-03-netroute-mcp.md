# NetRoute MCP Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let ChatGPT inspect and control NetRoute while command communication recovers through a working configured connection, beginning with proof that phone HTTPS and DNS work when LAN fails with Smart active.

**Architecture:** An authenticated remote MCP relay queues bounded requests for a Windows agent that connects outward over explicitly selected adapters. Both the agent and existing UI use the application's control service; durable operation records make interrupted writes recoverable without blind replay. Command recovery never changes the ordinary traffic profile.

**Tech Stack:** .NET 10; Windows/WPF existing application; ASP.NET Core and official `ModelContextProtocol.AspNetCore` SDK for the relay; `Microsoft.Data.Sqlite` journals; xUnit and existing fake-time conventions. No Python/Node runtime dependency in the installed widget.

**Spec:** [NetRoute MCP design](../specs/2026-11-03-netroute-mcp-design.md). Read the entire design before implementation. This plan is based on design commit `eb07efd`; the owner's 2026-11-03 instruction accepts it as the basis for planning.

**Status:** Plan only. Every implementation checkbox below is open. The feasibility check has not been performed and no MCP code has been created.

## Global Constraints

- “The owner clarified that automatic fallback is for **communication with NetRoute itself**.”
- “The promise is **automatic reconnection and recoverable command results**, not uninterrupted sockets or a guaranteed answer within every ChatGPT timeout.”
- “The first release requires an IPv4-capable working path, matching the existing Smart data path; IPv6-only reachability is reported as unsupported, not silently routed elsewhere.”
- “No force-to-known-dead-target option in v1.”
- “Use at-least-once delivery with deduplication, not an ‘exactly once’ claim.”
- One owner/paired PC initially; configured `lan`, `wifi`, `phone` slots only. Do not treat a NetRoute TUN or arbitrary VPN as a physical candidate. `windows_default` is a routing preference, not an adapter.
- Ordinary mode, metrics, Smart preference, auto-heal policy, and LAN local-subnet pins are unchanged by command recovery. Existing UI behavior, including explicitly retrying a sticky preferred connection, remains intact.
- Shared DTO/persistence and relay projects target `net10.0`; Windows components remain `net10.0-windows`. Relay must not reference `NetRoute.Core` or WPF.
- Protocol/package versions are pinned at Task 1 and captured in lock files; validate against official references S1–S7 in the design and the actual intended ChatGPT client. No floating package versions and no handwritten MCP protocol stack. Reuse existing test-package versions unless compatibility evidence requires a change.
- Recovery priority LAN → Wi-Fi → phone; 10-second long poll, 12-second stall deadline, 5-second candidate attempt, 20-second conditional recovery target; preferred-path probes every 30 seconds and three successes spanning at least 60 seconds before returning. Offline delays 1/2/4/8/16/30 seconds with jitter.
- Reads: 8-second deadline. Write acceptance: 2 seconds. Device freshness for writes: 15 seconds. Writes must start within 30 seconds of relay acceptance. Runtime settle verification: 15 seconds. Terminal results: 7 days; request-key/hash tombstones survive until unpairing. One active mutation, at most 10 additionally accepted writes per device.
- Request/response envelope limit 256 KiB. Usage: inclusive PC-local dates, at most 35 days, page size default 20/max 100, snapshot cursor lifetime 5 minutes. Unsupported/unrecorded is not zero.
- MCP is off by default; separate read/configure grants and distinct user/device credentials. Never put tokens in commands, repository files, output captures, or logs. No automatic installation of a service or creation of a public listing.
- Implementation uses an isolated worktree at execution time. Reuse the current main chat; no relay chats. This planning task neither deploys hosting nor interrupts the owner's network.

## Review Focus

1. **A phone source address is selected, but traffic still crosses the TUN or failed LAN.** Require adapter capture and an authenticated external response, including fresh DNS; Tasks 1 and 3 own this evidence.
2. **USB tethering reconnects with a different address/index during a long poll.** Retire the old pool and ignore obsolete probe results; Task 3 owns generation tests.
3. **A delayed/replayed command follows a local UI change or a crash.** Never overwrite the newer choice; Tasks 4, 6 and 9 test revisions, deduplication, partial outcomes and recovery.
4. **The PC sleeps or its clock changes near command expiry.** Resume cannot grant an old write a fresh lifetime; Task 6 tests fail-closed expiry with fake wall/monotonic clocks.
5. **A monthly report includes days before recording, Smart-off periods, or a timezone change.** Report missing/unknown coverage and consistent byte totals; Task 5 owns these tests.

## Verification conventions

Each task's red/green cycle is: add the named behavior tests, run the focused command and confirm a meaningful assertion failure (a missing type is an initial scaffold failure only), implement the specified interfaces, rerun to pass, then commit only the task's files. Reuse fakes in `tests/NetRoute.Core.Tests/Fakes.cs` and `SmartFakes.cs`; add focused `McpFakes.cs` as needed. Time-dependent unit tests use `FakeTimeProvider`, not real sleeps.

Unit command shorthand below denotes real commands, not future scripts:

```powershell
dotnet test tests/NetRoute.Core.Tests --filter "Category!=Integration&FullyQualifiedName~CLASS"
dotnet test tests/NetRoute.Mcp.Contracts.Tests
dotnet test tests/NetRoute.Mcp.Persistence.Tests
dotnet test tests/NetRoute.Mcp.Relay.Tests --filter "Category!=Integration"
dotnet test tests/NetRoute.App.Tests --filter "Category!=Integration"
```

Replace `CLASS` with the task's named test class. The final milestone runs the combined non-integration solution suite. Integration tests that disconnect networks, change profile settings, or deploy endpoints are opt-in, never part of routine `dotnet test`.
