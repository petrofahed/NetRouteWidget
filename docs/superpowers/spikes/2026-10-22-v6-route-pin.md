# v6 route-pin spike — results

**Date:** 2026-10-22
**Machine:** the user's PC, Ethernet and Wi-Fi 2 both joined to pzhome (Google Wifi, 192.168.86.0/24). NetRoute was running in LAN mode with Smart routing on (sing-box's `NetRoute` TUN was carrying internet traffic throughout).

## Step 1: starting state

```
InterfaceAlias AutomaticMetric InterfaceMetric
-------------- --------------- ---------------
Wi-Fi 2                Enabled              35
Ethernet              Disabled               5

InterfaceAlias RouteMetric PolicyStore
-------------- ----------- -----------
Wi-Fi 2                256
Ethernet               256

Find-NetRoute 192.168.86.1 → Ethernet
Find-NetRoute 1.1.1.1      → NetRoute (sing-box TUN)
```

Both interfaces carry an on-link `192.168.86.0/24` route at the default RouteMetric 256, as expected.

## Step 2: simulate Wi-Fi mode — confirm the bug

Set Wi-Fi 2 to metric 5, Ethernet to metric 50 (today's two-way `MetricPolicy`, Wi-Fi preferred).

```
Find-NetRoute 192.168.86.1 → Wi-Fi 2   ← local traffic would leave over Wi-Fi
Find-NetRoute 1.1.1.1      → NetRoute
```

Confirms the design doc's problem: with Wi-Fi preferred, Windows' own route selection sends LAN-subnet traffic (cameras, etc.) out over Wi-Fi too, because both adapters are on-link for that subnet and metric is the only tiebreaker.

Note: `1.1.1.1` always resolves to `NetRoute` while Smart routing is on, regardless of interface metric — sing-box's TUN installs its own higher-priority default route. This matches the spec's analysis: sing-box excludes private ranges (`route_exclude_address` includes `192.168.0.0/16`) from the TUN, so **local-subnet traffic is the only thing actually decided by interface metric**, whether Smart routing is on or off.

## Step 3: apply mechanism A (lower the LAN's on-link route metric)

```powershell
Set-NetRoute -InterfaceAlias 'Ethernet' -DestinationPrefix 192.168.86.0/24 -PolicyStore ActiveStore -RouteMetric 0
```

```
Find-NetRoute 192.168.86.1 → Ethernet   ✓ fixed
Find-NetRoute 1.1.1.1      → NetRoute   (unchanged, as expected)

ping -n 15 192.168.86.1: 15 sent, 15 received, 0% loss, 0 ms
Ethernet SentUnicastPackets: 1,181,692 → 1,189,699 (Δ 8,007) across the ping run
```

The adapter counter rising confirms traffic actually left over Ethernet, not just that route selection reported it would.

## Step 4: with Smart routing running

Smart routing was running for the whole of Steps 1–3 (confirmed by `1.1.1.1 → NetRoute` throughout). The pin held with it running: local traffic went over Ethernet, internet traffic went through the TUN as usual. No separate test was needed once Step 2 established that sing-box never touches the 192.168.0.0/16 range.

## Step 5: survives a DHCP renewal

**Not run.** Renewing the Ethernet lease (`ipconfig /renew Ethernet`) would have briefly interrupted the user's live local network while they were working, for no decision-relevant information: the plan already says "either result is fine, because Task 8 re-applies the pin on every refresh." Task 8's design (`RoutePin.Sync`, called every `RefreshAsync`) does not depend on the answer — a reset-by-renewal is simply one more case `Sync` re-pins on its next poll, same as a reset by any other cause. Skipped as a judgement call; it does not change the Step 7 decision below.

## Step 6: revert

```powershell
Set-NetRoute -InterfaceAlias 'Ethernet' -DestinationPrefix 192.168.86.0/24 -PolicyStore ActiveStore -RouteMetric 256
Set-NetIPInterface -InterfaceAlias 'Wi-Fi 2' -AddressFamily IPv4 -AutomaticMetric Enabled
Set-NetIPInterface -InterfaceAlias 'Ethernet' -AddressFamily IPv4 -InterfaceMetric 5   # NetRoute's own LAN-mode metric, left as NetRoute had it
```

Confirmed back to NetRoute's normal LAN-mode state (Ethernet metric 5, fixed; Wi-Fi 2 automatic; both on-link routes back at 256).

## Decision

**Mechanism A (lower the LAN's on-link subnet route metric to 0 in `ActiveStore`, default 256) works**, with Smart routing both running and not needed to be separately toggled off (it never saw the local subnet in the first place).

- `RoutePin.PinnedMetric = 0`
- `RoutePin.DefaultMetric = 256`

Task 8 proceeds as written.
