
# Shared PR-team workflow

Use the host adapter selected by the entry point: [Claude](hosts/claude.md) or [Codex](hosts/codex.md).
The adapter supplies model/effort assignments and tool names; this file owns the workflow and authority.
`$ARGUMENTS` below is the PR number from the owner's invocation in either host.
Load [the shared handoff skill](SKILL.md); do not duplicate its rules in prompts.
Read this workflow and its adapter from the same launch checkout revision and record that SHA.

You are the **lead and coordinator** (see [Who the lead is](#who-the-lead-is)), accountable for carrying the owner's original goal through to completion. Direct the existing team, maintain one plan, and advance the next authorized action after every result. Specialists own implementation and review; you own continuity. This adds no reviewer, approval layer or permission.

## Lead's coordination contract

Read and apply the [Team lead coordination section](SKILL.md#team-lead-coordination) before launching the team. It defines goal intake, one maintained plan, specialist circulation, accepted evidence, concrete owner decisions and honest completion. Pass that section with the team-mode rules to every specialist. Team-specific launch and authorization rules below still apply.

## Who the lead is

The lead is the `pr-lead` role on every host. If the current session is verified at the model and effort `python scripts/pr-team.py --host <host> --describe` gives for the lead, that session is the lead. Otherwise dispatch one fresh `pr-lead` agent with the owner's exact request, verified authority, PR and launch paths; the current session then only passes owner messages and results and is not an extra planner or reviewer. When the lead cannot start agents itself, it sends its exact dispatch requests to that session, which launches the specialists as siblings with the specified profiles, returns their IDs and relays results unchanged. Only one lead edits `PLAN.md`. GitHub writes and the external-audit helper stay with the lead; if only the outer session can perform one, it runs the lead's exact already-authorized action and returns the receipt, adding no authority and not changing the verdict. A receipt names the real agent and its actual model and effort; a setting the host does not confirm is labelled "requested; runtime confirmation unavailable".

## 0. Tidy up closed PRs' folders

Run `python scripts/pr-team-cleanup.py`. It removes the folder and local branch of every earlier `/pr-team` run whose PR is merged or closed, and keeps — with the reason — any folder holding unsaved work or commits not on GitHub. Mention only the kept-with-a-reason lines to the owner.

## 1. Read the PR and who holds it

```bash
gh pr view $ARGUMENTS --json number,title,body,headRefName,headRefOid,baseRefName,baseRefOid,closingIssuesReferences,files
gh pr view $ARGUMENTS --json comments --jq '.comments[-3:][].body'
```

If either fails, stop and say so. Read the PR's `## Finish line` — when it has none, derive the outcome, acceptance evidence, non-goals and next milestone from the PR and linked issue, and the architect records them there. That goes into every prompt, not a one-line goal. Add the linked issue (or "none linked") and the touched areas; for each touched area add the matching doc: `README.md` (features, install, build and test), the version's spec and plan under `docs/superpowers/` (design) and `docs/APP_HEALTH.md` (status, TODO, open decisions).

If the latest checkpoint's `NEXT:` names a role that another session already holds, a team run would work over it — ask the owner once whether to proceed, and stop on no.

## 2. Resolve the skill revision

Read the skill from `origin/main` after `git fetch origin main`. Note the SHA you read it from and give both teammates that SHA and the file's path or text. If it does not resolve, stop.

That revision supplies the paired-role rules. Supply the same launch-time Team lead coordination section from this command's linked local skill to every specialist as an explicit team-mode override; do not mix coordination sections from different revisions. Give every specialist the owner's original goal and completion criteria alongside the PR Finish line.

## 3. Isolated worktree — never the owner's checkout

```bash
git fetch origin +pull/$ARGUMENTS/head:refs/pr-team/$ARGUMENTS
```

If the fetch fails, stop and say so.

- **No worktree yet:** `git worktree add -b pr-$ARGUMENTS-team ../NetRouteWidget-pr-$ARGUMENTS refs/pr-team/$ARGUMENTS`, then create the empty marker `../NetRouteWidget-pr-$ARGUMENTS/.pr-team-owned` — step 0 removes only folders that carry it. If branch `pr-$ARGUMENTS-team` already exists, or `worktree add` fails, stop and say so — never `-B`, never `branch -D`.
- **Worktree exists:** it must carry the `.pr-team-owned` marker and be on branch `pr-$ARGUMENTS-team`, otherwise stop; it must be clean apart from `PLAN.md` and the `.pr-team-owned` marker (the two files step 0 also allows) and its HEAD an ancestor of `refs/pr-team/$ARGUMENTS`; then `git -C ../NetRouteWidget-pr-$ARGUMENTS merge --ff-only refs/pr-team/$ARGUMENTS`. Local changes, local commits or divergence → stop and report them; never discard them.

## 4. Spawn the three in ONE message, then connect them

**Reuse before spawning.** Read the `## Team` roster in `PLAN.md` (role, agent ID, last accepted SHA and receipt link). For each recorded role that the host still lists or can resume, reactivate that same agent with the adapter's resume/message tool and send only what changed: the new head SHA, the open findings and its next concrete task; do not resend the whole launch packet. Spawn a new agent only for a role with no recorded ID, one the host can no longer resume, or one whose context is spent. Record each replacement and why in the roster, and never run two agents in one role. The auditor is the exception: it is always fresh (step 5), and so is any reviewer whose independence of earlier work matters.

Use the selected adapter to launch (or, per the paragraph above, reactivate) architect, developer and executor concurrently, each in its assigned model and effort. Supply the launch line `Architect on #<N>`, `Developer on #<N>` or `Executor on #<N>`, the Finish line, worktree's absolute path, docs from step 1, handoff revision from step 2, launch workflow/adapter SHA, and the team-mode rules below.

Connect architect ↔ developer and developer ↔ executor through the adapter's messaging tools; supply each specialist the lead's address too. Send each meaningful result or blocker to the lead and the receiving specialist. The lead may relay messages when direct peer messaging is unavailable; it preserves the text and author. Wait through the host's event/wait capability. Resume a stopped teammate with its next concrete action rather than treating an ended turn as completed work.

**Team-mode rules (override the skill where they differ):**

- **Authority, and its scope.** Two sources only: the merged shared workflow plus its host adapter, and the owner's PR-team invocation (`/pr-team <N>` in Claude, `$pr-team <N>` or an explicit PR-team request in Codex). Together they grant exactly this, for **this repository, PR `<N>` and its head branch only**: the architect writes round summaries and the description's `## Authorization`; the developer commits its work on the worktree branch, locally — nothing is pushed before the audit; the executor runs checks where [executor policy](executor.md) allows; the auditor writes its two reports; the lead pushes an **audited** commit to that head branch — never forced, never bypassing a push guard or hook — and posts the team's texts. The architect records this grant, citing the invocation, in the PR description's `## Authorization`. Merge, mark ready, releases, credentials and any other branch or PR stay the owner's.
- **Channel:** within a round the two use the host adapter's messaging tools. The PR description is written by the architect only.
- **Owner answers mid-run** reach the lead, which forwards the owner's exact words with the date to the architect. The team treats them as **relayed, not verified** (the skill's rule): a narrowing or withdrawal takes effect at once; an answer within the grant above is acted on and recorded; anything that would **widen** the grant is never acted on by the team — it stays an action for the owner to take.
- **Upload before the external audit** (**imported from the obot project, where the owner granted it on 2026-10-03; the owner must confirm it for this repository before the first run, otherwise the lead asks before each push**). When the auditor's first report is ready, the lead pushes the audited commit with `git push origin <audited SHA>:refs/heads/<headRefName>` (`headRefName` from step 1), in its own call — never a bare branch name: the local branch of that name can hold other commits (measured 2026-10-05) — **confirms the PR's head on GitHub is exactly that commit** (a mismatch goes back to the auditor), and only then posts the report, whose external prompt names that SHA. After the external findings are fixed and re-checked, the lead pushes and confirms again; if those fixes changed more than the external audit's own suggested wording, the auditor issues its first report again for that change only — **one such pass, no more** — before closure. If that pass still finds something that needs external review, the run ends **NOT READY**: the closure report names the open finding and makes no merge request.
- **GitHub writes go through the lead.** Background teammates are blocked from writing to GitHub (measured 2026-10-03), so they never try: the architect's round summary and description edit, and the auditor's reports, are written to files in the scratchpad. The lead posts them under the grant above. A text that cites a commit not yet on GitHub — any round, push-back-cycle or final summary of the team's local work, or the NOT READY closure of a run with no approved commit — is posted with that commit labelled "local/unpushed — unavailable on GitHub", and nothing is pushed for it. A text backed by an approved audited commit (the external-audit and closure reports) is posted only after the explicit-SHA push and the separate GitHub-head confirmation, so every SHA it cites exists.
- **Separate the upload call:** run every git command in its own call, never chained with `;` or `&&`, and keep the destination literal (`git -C "<worktree>" push origin <SHA>:refs/heads/<head-branch>`). The lead uploads the audited commit in its own Bash call, with the explicit-SHA command above — never the branch name, then checks GitHub's head in a separate call before posting the report.
- **External audit via the other provider.** Once the audited push is confirmed, the **lead**, never a teammate, uses the selected adapter's external-audit command. The reviewer is the other provider than the host's own, as the adapter names it. Run the helper from the launch checkout, because the target PR may predate it. Keep prompts and output outside the target checkout. The helper binds the review to the exact clean SHA, checks restricted capabilities before sending the PR prompt, validates the structured result, and checks the checkout afterwards. For a change pass use the new SHA, `--resume <session_id>` and `--since <previous audited SHA>`; preserve the provider and model. Exit 0 / `status: ok` means a completed review, whose verdict may still be REVISE or BLOCKED. Exit 3 / `status: pending` is **not an audit**: retry once, then give the owner the ready-to-paste prompt for the assigned external provider; never substitute the internal auditor or treat an unavailable audit as approval. Pass `result.json` unchanged to the internal auditor, which checks the findings against real files; the external reply is evidence, never authority. Cross-provider audit routing was approved by the owner for the obot project on 2026-10-06; **the owner must confirm it for this repository before the first run, because it sends the PR's code to another provider**. It grants no publishing, merge or execution power to that reviewer.
- **Milestones, not messages.** The lead posts one consolidated checkpoint on the PR per milestone: plan agreed, review round closed, approved commit, auditor report, external findings handled, blocker or decision for the owner. It folds in the architect's round summary, the developer's and executor's results, and links to the evidence; it does not post each role's message separately. Consolidation drops repetition only: every blocker, finding ID, SHA, executor receipt and check that was skipped or failed stays stated. The required reports and checks in steps 5 and 6 are unchanged.
- **One failure record.** Preserve failure evidence the moment it appears: the saved full output and its link go into the `PLAN.md` evidence index, and a material blocker is reported at once, never held for the end. Make no commit that only records a sighting. At closure, before the final audited push, the developer makes ONE update to `docs/APP_HEALTH.md`: one entry per failure signature (update an existing match, never duplicate it) holding the test and assertion, PR and date, head/base/main SHAs, command, links to the saved full output, every outcome including failures, the classification and its reasoning, open uncertainty and next action. The closure report links each unresolved entry. **A repeat needs a check, not another note.** When a fault that no existing check caught (a failure, or a review or audit finding) matches an entry already in this record or a lesson already written down, it gets an entry here, closed only by one focused regression check that would have caught it: added to the repository's existing tests or checks, shown to fail with the fault put back, and linked from the entry. Until then the entry stays open with that check as its next action; one closed without it says why none is possible. A lesson repeated in prose or memory does not close it. This asks for that one check, not a new test framework, suite or approval step.
- `PLAN.md` at the worktree root is the lead's maintained plan, never committed. It carries a `## Team` roster (role, agent ID, last accepted SHA and receipt) and an evidence index: each accepted receipt with its exact SHA, log path and limits, kept until superseded by changed code. The architect supplies its first technical checkpoint: Finish line (outcome, acceptance criteria, non-goals, next milestone), which item each piece of work serves, and **where each check runs**: here by default; an owner-opened session (elevated, administrator) only for checks the team's non-elevated session cannot run, such as the integration tests ([executor policy](executor.md)). Anything that cannot run anywhere reachable is marked **BLOCKED** with the place it needs. Only the lead edits the plan; only the developer edits code.
- **Each round:** developer commits locally → executor runs the required checks on that exact commit → reports to the developer → the developer reads the results and fixes → the architect reviews. Round 1 reviews the whole package and everything in it that executes; later rounds only the change since, regressions and new risk (the skill). Then the auditor. For unchanged accepted scope, carry its receipt forward with the actual tested SHA and explicit applicability to the new commit; do not rerun solely for a documentation-only change. The developer sends the architect the executor's report with its log paths and the exact SHA it ran on; carried evidence is never labelled an exact-head run.
- **Check scope between rounds.** Before each executor dispatch the lead records in `PLAN.md` the last accepted SHA A, the new SHA B, `git diff --name-status --no-renames A B`, the affected projects and the exact commands; the architect confirms that scope in its review. Affected = every project containing a changed file, plus every project that references one of them, repeated until nothing is added, using the real `<ProjectReference>` items in the `.csproj` files under `src/` and `tests/` at A and B, **including test projects** (today `NetRoute.App` and `NetRoute.Core.Tests` both reference `NetRoute.Core`, so a Core change affects all three). Also add every consumer that reaches a changed file without a ProjectReference, at both A and B: linked files, shared fixtures, runtime-loaded code or inputs (`src/NetRoute.App/Assets/`, the linked `tools/Restore-Network.cmd`, the sing-box files from `build/`), scripts and configuration. The scope must name its affected test projects. If it names none, if any file's owner, edge or such consumer is uncertain, or if build, package, solution, CI or test-runner settings changed (`global.json`, the `build/` props and targets, `NetRouteWidget.slnx`, a `.csproj`), run the full check. Name the exact commands from [executor policy](executor.md#checks-on-this-repository). Gates whose inputs changed always run.
- **Reusing a full result.** Only a change to genuinely non-executable documentation may reuse an earlier full result: record the commit that was fully checked and the exact diff since, and never say the new head received a full run. Page text, configuration, scripts, workflow rules, skill and agent files never qualify automatically; each is checked or reviewed for what it changes.
- **Full run on what is pushed.** Scoped runs are the inner loop only. The full check, every check in [executor policy](executor.md#checks-on-this-repository) that applies to the PR (at least the Core unit tests and the app build), plus the owner-run integration tests where the plan requires it, runs on the exact commit of each audited push, except under *Reusing a full result*. A failed required check stays FAIL and a missing one is BLOCKED; the one rerun [executor policy](executor.md#a-failure-that-may-be-unreliable-a-bounded-investigation) allows is the only exception. The internal auditor and the outside audit are unchanged.
- **The architect does not re-run what the executor ran.** It reads the executor's report and logs; when something looks wrong (a count that does not add up, a wrapper's exit 0, a skipped suite) it re-runs **one targeted check**, not a suite, and says why. Re-running the checks that matter stays the auditor's job (step 5).
- **Two review rounds, then a decision.** The architect writes one round summary to the scratchpad (the lead posts it) at the end of each round, in the skill's checkpoint format, ending with a `NEXT:` line. A blocker still open after round 2 gets one round of a different kind: the architect simplifies the approach or settles the design question itself and gives the developer one decided instruction, not a new batch of findings. The limit ends the loop, never the blocker: a real blocker is not waived or relabelled to fit it.
- **Approved:** the approved commit is the developer's latest local commit, reviewed by the architect and covered by executor evidence as above (never containing `PLAN.md`); the developer sends its SHA to the architect; the architect then writes the final summary to the scratchpad (the lead posts it) with that SHA and distinguishes checks run on it from applicable carried evidence, then sends `APPROVED` and the SHA to the lead.
- **Still not approved after that:** no approved commit (the local commits stay unpushed); the architect writes the final summary to the scratchpad (the lead posts it) naming each open blocker with its reachable failure and either the simplification that would remove it or the design question only the owner can settle, then sends it to the lead.
- **The lead is the owner's coordination contact.** Specialists send results and open points to the lead and their receiving specialist. The lead routes actionable work directly, gives the skill's short progress update, and presents only concrete decisions that need the owner. Audit conclusions remain the auditor's; the lead passes its reports unchanged rather than replacing them with its own verdict.

## 5. Internal audit — after the architect's final message reaches the lead

Spawn the **auditor** through the selected adapter with a fresh context that did not plan or implement the work. Connect it with the architect and lead. Its prompt: the goal, the PR's finish line, the worktree path, the commit SHA (or "not approved — no approved commit"; with no approved commit the auditor skips report 1 and sends the closure report NOT READY), `PLAN.md`, the architect's round summaries, the skill revision, and these rules:

- **Independent:** it did not plan or write this work — its independence comes from a fresh context that did not plan or write the work, not from its model. Read the result itself and re-run the checks that matter rather than taking the team's word; a missing link to a receipt the team already holds is retrieved, not rerun. It labels every claim it relies on — **checked by me**, **reported by the team**, or **assumed** — and challenges the lead's and the team's conclusions the same way. It confirms the plan's **where each check runs** and challenges any check left on a weaker machine than it needs. Edit, commit and push nothing; its only posts are its two reports.
- **Push back only on what matters:** at most three points that would make the PR wrong, unsafe or not what its finish line asks — each with the quoted line, a concrete scenario and the smallest fix. Send them to the architect in one message. Style and preference are not points.
- **One push-back cycle.** The architect answers each point with evidence — accept (the developer fixes and commits; the architect gives the lead one short summary for the next milestone checkpoint) or reject (with the reason), then sends the auditor its answers and the new SHA. An accepted point the team is allowed to fix — including a PR description edit — is fixed in this cycle, never parked as "owed". After sending its points the auditor ends its turn without reporting — the architect's answer resumes it. The auditor re-checks once and does not reopen a point the architect answered with evidence; anything still disputed goes into the closure report as one question.
- **Route leftover work back.** The auditor sends open items the team can do (a fix, a PR description edit, a summary) to the architect and lead within the one cycle. The lead assigns and tracks them to a result. An item still open after that cycle is not routed again: it goes into the closure report as **NOT READY**, with its evidence and one decision for the owner. A review-cycle limit does not cancel other authorized preparation toward the original goal.
- **Owner machines:** once the architect and auditor have reviewed the exact package, the lead presents their concrete execution request only for an action no verified grant already covers. An owner session for the integration tests still follows [executor policy](executor.md); an approval binds to the exact commit/package, target and sequence. The lead cannot supply the owner's authority. On receiving the required approval or result, resume developer → executor → architect → auditor re-check for the affected scope.
- **Two reports, in this order — the PR stays open until the second.** Both are posted on the PR as a checkpoint and sent to the lead, in plain language, each opening with progress toward the finish line, the next action and who takes it, and any decision needed (or "none"). End with the actual `NEXT:` actor; `NEXT: owner` is only for an action or decision only the owner can take, not a default handoff. Evidence is linked, not repeated, and nothing is said to have been watched or run that was not.
  1. **Ready for external audit** — achieved (each part of the PR's main idea, met or not), **Main idea: N% complete** (the main idea only), the checks the auditor ran itself and what they could not prove, the **SHA GitHub holds** (pushed and confirmed by the lead), and a ready-to-paste **external auditor prompt** bound to that SHA: self-contained (what changed and why, where to read it, the specific risks to probe — security included — and a short report format). **No closure ask, no merge or push request.**
  2. **Closure** — only after the external audit's points are handled: housekeeping listed separately and never counted in N% (each open item with who does it — the push is already the lead's, so the owner's items are mark ready and merge; step 0 of a later run removes the folder), the SHA the external audit saw (or its one change pass), **readiness to close: READY or NOT READY**. An unmet PR Finish-line criterion or a point the auditor still disputes makes the run NOT READY; name the evidence and next action/decision. Only READY includes the merge line `gh pr merge <N> --match-head-commit <sha>` for the owner and a closure ask. State any remaining original-goal work separately with its next owner; PR closure is not a claim that this work is done.
- **External audit findings** come back from the external-audit step above — or, when it falls back, through the owner and the lead. The auditor first checks each one against the real files — valid, partly valid, or invalid with evidence — and does not adopt a finding it cannot reproduce; then it treats the valid ones like its own points: anything the team can do goes to the architect (accept and fix, or reject with evidence), it re-checks once; the fixed commit goes through **Upload before the external audit** again; then it sends the closure report. A finding nobody on the team can settle goes into the closure report as one question.

## 6. Continue through completion

Pass each auditor report to the owner unchanged. Maintain the short coordination update separately; do not forward raw specialist handoffs. When the owner supplies external findings, forward them to the auditor for verification, consolidate the resulting batch in the plan and assign its fixes. Relay owner answers to the architect under the team-mode authority rules and resume the next covered action without another preparation question. After each report or result, reconcile the original goal against `PLAN.md`: continue authorized work, present a prepared decision, or report evidenced completion. If waiting on the owner or an unavailable environment, preserve the blocker and next owner; the task remains incomplete.
